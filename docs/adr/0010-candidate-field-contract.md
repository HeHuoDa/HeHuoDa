# ADR 0010：采集候选字段契约 v2（name / eventKind / scope / mode）

## 状态

采用

- 日期：2026-11-09
- 关联：Issue #203（本 ADR 即其第一阶段交付）、Issue #198（缺陷 1/2/3/5）、Issue #202 / PR #207、ADR 0004（候选与正式比赛分离）、ADR 0009（赛事性质与验收口径分离）、[quality-eval-protocol.md](../quality-eval-protocol.md) 3.3／3.4
- 基线：`main` `7b7973c34b777d5fcad05891969dcc20845f0818`，规则版本 `competition-rules-5`
- 后续修订：Issue #206 阶段一把自动提取范围收敛到七个字段（见下方「2026-11-13 修订」），规则版本升到 `competition-rules-17`

## 2026-11-13 修订：七字段辅助录入范围（#206）

本节是**现行权威范围定义**；下方 v2 契约、scope 四值、eventKind 语义、name 剥离与 mode 归一仍描述字段形状和已确认规则，但只有本节列为保留的七个字段继续产出确定值。

| 字段                                                | 本期状态             | 未确定时的表现                                      |
| --------------------------------------------------- | -------------------- | --------------------------------------------------- |
| `name` / `edition` / `organizer`                    | 保留，明确证据下预填 | 空串 / `null`，管理员确认                           |
| `members` / `scope` / `hosts`                       | 保留，作为审核提示   | `null` / `unknown` / `[]`                           |
| `tracks`                                            | 只保留 `name`        | `[]`；嵌套 `modeKind`/`members`/`rules` 恒为 `null` |
| `eventKind` / `mode` / `modeKind`                   | 退出一期自动提取     | `null`                                              |
| `rules` / `stageNames`                              | 退出一期自动提取     | `[]`                                                |
| `startsAt` / `deadline` / `materialsAt` / `eventAt` | 退出一期自动提取     | 既有未知 `TimeValue`                                |

四条实现与验收约束：

1. 收敛只有一个咽喉：`applyCandidateScope` 在 `parseCandidate` 与 `parseEvidenceCandidate` 两个对外入口末尾执行。正文解析、附件合并、首次入库与非赛事快照重提取共用同一判据，不得由调用方各自裁剪。`parseCandidateUnscoped` / `parseEvidenceCandidateUnscoped` 只供规则回归测试与内部备选值聚合，不是采集入口。
2. 退役不等于隐藏证据。退役字段只清空**取值**，正文与附件的定位证据继续随候选保存并展示，管理员据此人工填写正式记录；这与「旧证据和历史材料不能因新展示策略被隐藏」一致。
3. 退役不等于正文缺信息。退役字段不再计入 `missing`（待补缺项），也不再逐字段产生清理冲突，改由一条统一的「本期不自动提取」说明告知；管理端展示层同样用说明行而不是「未提取」，避免把停用误读成正文缺失或解析失败。
4. 保留字段的确定值必须有据。`scope` 与 `hosts` 的既有争议按原文逐条复核；无法由契约归一的情形保留 `other`／空值加原文，并记为 `unreviewed` 而不是缺陷；不能靠把七个字段清空来「通过」。

本期不新增采样、不设任意准确率或覆盖率下限，结论只称「七字段辅助录入闭环通过／未通过」。完全退出范围的九个字段不再优化，相关新问题登记后另行决定。

## 背景

#198 在独立验证集上确认四处「实现不符合协议」，不是可接受的口径差：

| #   | 缺陷          | 现状                                                  | 协议要求                                  |
| --- | ------------- | ----------------------------------------------------- | ----------------------------------------- |
| 1   | `scope.kind`  | `all` / `colleges` / `complex` / `unknown`            | `all` / `specified` / `other` / `unknown` |
| 2   | `fields.kind` | 写入 `registration/supplement/award/news`（通知种类） | 赛事种类／项目类型                        |
| 3   | `fields.name` | `name = article.title`（含「关于举办…的通知」套语）   | 比赛名称                                  |
| 5   | `fields.mode` | 英文枚举 `individual/team/mixed`                      | 字符串：参赛形式（个人／团队等）          |

同时 `fields.kind` 被三处当作通知种类消费：审核队列优先级、管理端标签、正式 `Notice.kind` 的来源。协议侧 `notificationKind` 只出现在 `classification`，而 `store.ts` 的非赛事分支重新调用 `parseCandidate` 时不带分类结果，导致候选缺少 `classification`——通知种类出现第二个隐含来源。

六项决策已确认（2026-11-09，用户在本票会话内逐项确认）：

1. scope 采用协议四值，正式比赛模型不变；
2. 新契约用 `eventKind` 承载赛事种类，通知种类唯一来源为 `classification.notificationKind`；
3. eventKind 先定语义，禁止混用学科大类、组别、赛段与选拔层级；不按 gold 命中率选规则；
4. name 只剥离可确认的通知套语；
5. mode 保留原文，另存可靠归一的 `modeKind`；
6. 用 `fieldsContract` 标记契约，规则版本按当时最新 main 递增，HTTP 兼容投影覆盖 kind／scope／mode，兼容层保留至 #204 验证通过。

## 决策

### 1. 候选字段结构（v2）

`ParsedCandidate` 增加 `fieldsContract: "candidate-fields-v2"`；`CandidateFields` 调整为：

```ts
interface CandidateFields {
  name: string;                  // 赛事名，已剥离可确认的通知套语
  edition: string | null;
  eventKind: string | null;      // 赛事种类／项目类型，原文短语
  organizer: string | null;
  hosts: string[];               // 承办学院，仍不得由发布网站推断
  scope: {
    kind: "all" | "specified" | "other" | "unknown";
    colleges: string[];          // 只放允许参赛学院
    note: string;                // 原文或核对说明
  };
  mode: string | null;           // 参赛形式原文短语
  modeKind: "individual" | "team" | "mixed" | null;  // 可靠归一结果
  tracks: { name; modeKind; members; rules }[];
  members: string | null;
  rules: string[];
  stageNames: string[];
  startsAt / deadline / materialsAt / eventAt: TimeValue;
}
```

`CandidateFields` 不再有 `kind`。通知种类只从 `ParsedCandidate.classification.notificationKind` 读取。

### 2. scope：四值边界

| 情形                                                                                                                   | kind        | colleges                    | note               |
| ---------------------------------------------------------------------------------------------------------------------- | ----------- | --------------------------- | ------------------ |
| 明示全校，且无「仅／限／除／不含／校区」等收窄                                                                         | `all`       | `[]`                        | 原文               |
| 命中学院目录，且无否定／排除语义                                                                                       | `specified` | 命中的学院 ID（去重、排序） | 原文               |
| 有明确限制但无法枚举为学院列表（否定／排除、禁入学院、未知学院名、年级／专业／校区／班级等非学院限定、多条款不可合并） | `other`     | **恒为 `[]`**               | 原文，保留全部限制 |
| 缺乏资格依据：无资格条款、只有小节标题、跨来源不可关联、证据冲突且不可合并                                             | `unknown`   | `[]`                        | 核对说明           |

- 否定／排除、禁入学院、未知学院名**一律不写入 `colleges`**。
- 年级／专业属于人群口径（ADR 0009 的 `audience` 维度），不因出现年级限定就把已命中的学院降级为 `other`；只有否定／排除和无法枚举的学院表述才降级。
- `specified` 的 `colleges` 必须非空；空则退回 `other`。
- 不从发布学院、来源站点或 URL 反推参赛范围（沿用 `GLOSSARY.md`）。

### 3. eventKind：语义先定、只用可解释来源

`eventKind` 表达**赛事种类／项目类型**（学科竞赛、创新创业、职业规划技能、艺术文化、体育等大类，或原文明确的项目类型），**不表达**：

- 阶段与赛段（初赛／复赛／决赛／院赛／校赛）；
- 选拔层级（院级／校级／省级／国家级选拔赛）；
- 组别与人群（新生组、研究生组、专业组）；
- 届次与年份；
- 通知种类（报名／补充／获奖／新闻）。

提取只允许正文中**可核对**的显式标注：

1. 正文显式标注：`赛事种类|竞赛类型|比赛类型|项目类型|赛事类别` 后接冒号的取值；
2. 无 (1) 时返回 `null`。

暂不启用「从标题派生赛事种类」的宽泛模式：标题里可解释的赛事种类短语与阶段、层级、组别的切分尚无确认规则，派生会把「院级研究生选拔赛」这类选拔层级当成种类。宁可 `null`，也不猜。`null` 表示「未提取」，不等于「非赛事」。

### 4. name：只剥离可确认的通知套语

剥离规则（可重复应用，结果不得为空，空则回退标题原文）：

- 前缀：`关于举办`、`关于开展`、`关于组织参加`、`关于举行`；裸 `关于` 仅在整句标题为「关于{主题}的通知」框架时剔除（#206）
- 后缀：`的通知`、`的预通知`、`的补充通知`、`的变更通知`、`的更正通知`、`通知`；沿用既有入口回归确认的 `报名通知`／`参赛通知` 后缀，不额外吞掉赛事名末尾的「遴选／组织／评选」等区分信息
- 副标题：含 `——`／`—` 分隔符时按段分别剥离套语，再用规范分隔符拼接（`…决赛的通知 ——副标题` → `…决赛——副标题`）
- 派生前提（#206）：标题自身必须含赛事词（竞赛／比赛／大赛／挑战杯挑战赛／运动会等），否则不派生 `name` 与 `edition`；`关于做好…工作`、`关于开展…培训` 这类事务标题即使能剔出短句也不是赛事名

保留：

- 发文单位（`食品学院关于举办…` 中的「食品学院」）；
- 年份与届次（`2026年`、`第十五届`）；
- 「校内选拔赛」「院级选拔赛」等选拔层级与子赛道（`（创新创业类）`）；
- 引号内的赛事全名。

理由：删掉「校内选拔赛」会把「X 校内选拔赛」与「X」合并为同一比赛；发文单位是否为赛事名组成部分无法可靠区分时保留。

### 5. mode：原文 + modeKind

- `mode` 保存原文短语（如「团队」「团队形式」「每个小班组成一支队伍」「个人作品或集体作品」「个人或自行组队」），协议 `fields.mode` 比较这一层。
- `modeKind` 保存可靠归一结果：`individual` / `team` / `mixed` / `null`。
- 明确否定（「不组队」「不得以个人参赛」）先按否定处理再归一。
- 同一通知内出现互不覆盖、无法合并的多种形式时，`mode` 保留原文并记冲突，`modeKind = null`；只有同一句同时允许个人与团队（「个人赛及团队赛」）才归 `mixed`。
- `modeKind = null` 时，正式赛道不得自动生成，导入必须由人工填写 `individual/team/mixed`。

### 6. 版本、兼容与失效

| 项           | 决定                                                                                                                                                                                                                                                                                                                          |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 契约标记     | 新候选写 `fieldsContract: "candidate-fields-v2"`；缺该键即为 v1                                                                                                                                                                                                                                                               |
| 规则版本     | `competition-rules-5` → `competition-rules-8`（本地 v6/v7 评审修复后再递增）；沿现有提取键使旧快照与 v6/v7 候选重算。后续语义修订继续递增，当前版本以 `packages/sicau-connectors/src/notices/classification.ts` 的 `noticeRuleVersion` 与 [sicau-connectors.md](../sicau-connectors.md) 变更记录为准，本 ADR 不固化具体版本号 |
| 输出范围     | 只有上方「2026-11-13 修订」列出的七个字段产出确定值；退役字段的取值恒为契约空值，但定位证据仍保存。范围判定统一由 `applyCandidateScope` 在 `parseCandidate`／`parseEvidenceCandidate` 末尾执行，调用方不得自行裁剪                                                                                                            |
| 旧批准       | 规则版本变化使 `approved_file` 失效，候选回 `pending`；历史审核修订与正式数据保留                                                                                                                                                                                                                                             |
| 旧候选读取   | 显式 v1 归一：`colleges→specified`、`complex→other`、`all→all`、`unknown→unknown`；v1 `kind` 只进 legacy 视图，**不得**当作 `eventKind`                                                                                                                                                                                       |
| 旧审核材料   | 继续按现有基线校验；契约或归一结果不一致时返回可行动错误（「审核文件过期…请重新导出」／「只读证据…被改动」），不静默接受                                                                                                                                                                                                      |
| 正式比赛模型 | 不变。`ScopeRecord` 仍为 `all/colleges/complex/unknown`                                                                                                                                                                                                                                                                       |

**导入映射（候选 → 正式）**，只允许以下四条：

| 候选 scope  | 正式 scope | 条件                                             |
| ----------- | ---------- | ------------------------------------------------ |
| `all`       | `all`      | `colleges` 必须为空                              |
| `specified` | `colleges` | `colleges` 必须非空                              |
| `other`     | `complex`  | 必须保留 `note` 原文；信息有损，仅保留原文可追溯 |
| `unknown`   | `unknown`  | —                                                |

禁止的有损映射：`other → colleges`、`unknown → all`、空 `specified → all`、把否定／排除学院写入 `colleges`。

### 7. HTTP 过渡契约（保留至 #204 验证通过）

关键约束：**旧客户端读取的键必须保持旧形状**。旧管理端读的是 `fields.kind`、`fields.scope`（正式四值）与 `fields.mode`（英文枚举）。把新契约直接放进 `fields`、再另开 `legacyFields`，并不能让旧客户端“不改代码仍可运行”——它不会去读新键。因此 `fields` 保持 v1 形状，v2 契约放在新键里：

| 字段             | 内容                    | 说明                                                                               |
| ---------------- | ----------------------- | ---------------------------------------------------------------------------------- |
| `fieldsContract` | `"candidate-fields-v2"` | 显式版本；v1 归一后同样标注                                                        |
| `fields`         | **旧形状（兼容投影）**  | `kind`=通知种类、`scope`=正式四值、`mode`=英文枚举；旧客户端按原路径读取即正确     |
| `fieldsV2`       | 协议契约                | `name`/`eventKind`/`scope`(四值)/`mode`(原文)/`modeKind`；新代码与新管理端只读这里 |
| `fieldsV2.kind`  | 不存在                  | 通知种类一律读 `classification.notificationKind`                                   |

`fields` 是从 `fieldsV2` 派生的只读投影：携带 `kind`（通知种类）、`scope`（正式四值）与 `mode`（英文枚举），不含 `eventKind`。它不回写候选、不进入正式数据；审核基线仍以归一后的 `fieldsV2` 为准，保证新契约候选可原样往返。

这样 #204 完成前，旧管理端无需改代码即可继续工作；#204 改为读 `fieldsV2` 后，再按本 ADR 清理 `fields` 投影。

## 后果

### 兼容应用回退边界

持久化候选的 canonical `fields` 已是 v2，HTTP 的旧形状投影不意味着任意旧应用可直接回退。裸 `7b7973c` 既不认识 v2 通知种类来源，也不会擦除后来 HTTP 审核快照中的 `fieldsV2`，**不能作为本次契约升级后的安全回退目标**。不通过删除新字段、历史审核材料或强制全量重扫来伪造兼容。

回退构建必须保留 v2/v1 读取、通知种类适配、预览与历史修订投影、双侧隐私擦除及现有批准基线校验。隔离验证可用 `6117a38` 为基础，保留其双侧擦除能力，再从本次交付版本带回以下兼容文件：

- `apps/api/src/ingestion/candidate-contract.ts`
- `apps/api/src/ingestion/review.ts`
- `apps/api/src/admin/admin-review.service.ts`
- `apps/api/src/ingestion/runner.ts`

这是保留旧 v6 解析器、带明确兼容补丁的回退候选，不是未经修改的 `6117a38`。独立构建后，用隔离测试库验证新版本写入 → 兼容旧应用列表/详情/分类/审核/批准/预览/导入 → 名单附件擦除，核对当前候选、提取历史、人工修订、批准材料、操作快照及 HTTP 均无残留，正式数据仍保留。记录基线、兼容文件哈希、命令与结果；无这些证据不得认定回退通过。

本票的隔离兼容验证不授权生产发布或回退。实际部署前由 #206／#143 为选定回退构建补齐可信 CI、可用归档、备份及明确授权；不能直接使用只有本机构建证据的候选替代生产准入。

**代价**：候选 `fields` 结构变化使 `ingestion_extraction_revisions`、`approved_file` 与历史审核材料的旧字段不可直接复用；候选在回访或显式 `reextract` 时按新规则重算，重算后旧批准失效，并非发布时自动全量重算；`eventKind` 因禁用宽泛派生而大多数为 `null`，该字段短期覆盖率低。

**收益**：通知种类只有一个来源，优先级、筛选、正式 `Notice.kind` 不会再被赛事种类串义；scope 与协议一致，否定与排除不再需要靠读 `note` 猜；`mode` 原文与归一分层，评估按原文比较、导入按枚举约束，两种用途不再争一个字段。

**不做**：不改冻结 gold、不改协议、不重开 #198；不重做正式比赛／赛段模型；不新增来源、OCR 或自动发布。#206 阶段一把自动提取收敛到七字段后，也不再优化退出范围的九个字段。

## 无法自动映射项（须人工或按未知处理）

| 项                                        | 现象                                                                | 处理                                                                                                           |
| ----------------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| gold `fields.kind` 混用学科大类与选拔层级 | gold 同时出现「大学生学科竞赛」与「院级研究生选拔赛」「院内选拔赛」 | `eventKind` 只按第 3 节正文显式标注提取；评估层按协议正常比较并计入一致率与分母，另加诊断分类供阅读；不改 gold |
| gold `fields.name` 口径不一               | 部分样本剥离套语，部分保留标题原文                                  | 评估层按协议正常比较并计入分母，套语差另列诊断分类；不因此豁免计分，也不据此放宽协议                           |
| gold `fields.mode` 为任意中文短语         | 「团队形式」「每个小班组成一支队伍」「个人作品或集体作品」          | 候选 `mode` 按原文比较并计入分母；`modeKind` 不参与 gold 比较，只约束导入                                      |
| scope 含非学院维度限制                    | 年级、专业、校区、班级                                              | `other` + 原文，不写入 `colleges`                                                                              |
| scope 只有小节标题                        | 「参赛对象与要求」                                                  | `unknown`，并保留小节标题证据                                                                                  |
| 跨来源资格小节                            | 资格标题与正文分属通知与附件                                        | `unknown`，两侧证据分别保留                                                                                    |

## 评估层口径（不改 gold）

- 协议 `fields.kind` 与候选 `eventKind` 对齐比较；`eventKind = null` 按未知处理，不计正确，也不计错误。
- 协议 `fields.mode` 与候选 `mode`（原文）比较，`modeKind` 不参与。
- 协议 `fields.scope` 与候选 `scope` 比较 `kind` 与排序后的 `colleges`；`other` 不因「取值模糊」被自动豁免，仍按 `unknown`↔`supported` 的过度确定规则裁决。
- 上述「无法自动映射项」只在报告里**额外**列出诊断分类，**不改变协议计分**：一致与否照协议判定，分母与错误数不变。要改变计分口径必须另行确认，本 ADR 不授权。
- 不允许通过修改 gold 或协议消除这些差异。
