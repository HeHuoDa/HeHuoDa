## 1. 项目目标与决策基线

### 1.1 项目定位

禾伙搭是一款面向四川农业大学学生的校园比赛与项目组队平台。学生可以按学院发现比赛，了解参赛范围，发布招募并完成申请、邀请和确认入队。

品牌名称暂采用“禾伙搭”，副标题为“川农比赛与项目组队平台”。名称尚未完成重名、商标和域名核查。平台按学生自建项目定位设计，不使用学校官方平台身份，不假设已经获得学校接口或统一认证授权。

### 1.2 开发目标

本项目优先证明独立完成前端、后端、数据库和部署的能力。第一版的成功标准是业务闭环可运行、核心规则正确、权限可验证、部署可复现，真实用户数量不作为开发验收前提。

重点展示四类能力：

1. 领域建模：区分比赛届次、赛道、承办学院、参赛范围、队伍、申请和成员。
2. 全栈交付：完成移动端界面、管理后台、接口文档、数据库迁移和部署。
3. 业务正确性：处理申请状态、邀请确认、队伍容量、重复提交和越权访问。
4. 工程验证：用自动化测试、并发测试和压测记录支撑技术结论。

### 1.4 本计划采用的技术默认值

为使任务能够直接拆分，本计划采用 NestJS + Fastify、Drizzle + PostgreSQL、微信一键登录与可轮换 Bearer 凭据。NestJS + Fastify 及首页所需 Drizzle + PostgreSQL 已落地；微信登录后端与凭据会话已随 #131 实现（默认关闭），小程序端前端接入已随 #132 落地；微信登录与统一身份认证已于 2026-10-26 在微信开发者工具完成真实核验，真机与生产环境仍待 #140 验收，不代表生产可用。

主要部署基线按单台 Linux、2 核 / 2GB 内存设计，最终资源配置由实际环境和压测结果决定。1GB 机器作为备选环境，需单独验证或另行评估 SQLite；不要求第一版同时兼容两种数据库。

### 1.5 当前本地启动方式

环境要求：Node.js `>=24.15.0 <25`、pnpm `10.30.3`。在 PowerShell 中执行：

```powershell
cd E:\HeHuoDa
corepack enable
pnpm install --frozen-lockfile
if (!(Test-Path apps/api/.env)) {
    Copy-Item apps/api/.env.example apps/api/.env
}
pnpm dev
```

依赖和环境变量准备后，根 `pnpm dev` 同时启动旧 Web/API；uni H5 单独执行 `pnpm --filter @hehuoda/uni dev:h5`，微信开发构建用 `pnpm --filter @hehuoda/uni dev:mp-weixin`，管理端用 `pnpm dev:admin`。启动新用户端与 API 可在两个终端分别运行，不由根 dev 自动选择。

- Web：[http://localhost:5173/health](http://localhost:5173/health)，端口占用时以 Vite 输出为准。
- API：[http://127.0.0.1:3001/api/v1/health](http://127.0.0.1:3001/api/v1/health)。
- Swagger：[http://127.0.0.1:3001/docs](http://127.0.0.1:3001/docs)。

仅 health 不需要数据库；首页查询需先按 README 启动 PostgreSQL、迁移并导入数据。API 默认监听本机，开发端口由 `apps/api/.env` 的 `PORT` 配置；修改 API 端口时同步设置 Web 的 `API_PROXY_TARGET`，默认值与代理入口见 `apps/web/vite.config.ts`，无需修改配置源码。更多检查命令见 [README](../README.md)。

## 2. 场景与需求依据

### 2.1 典型使用场景

- 学生知道自己所在学院，但不知道有哪些可以参加的比赛，希望按学院和参赛范围查找。
- 队长有一个参赛或课程项目，缺少编程、调研、设计、建模或答辩角色。
- 学生希望加入项目，但需要先了解目标、技能要求和合作方式。
- 管理员维护比赛来源，处理失效招募和举报。

### 2.2 学校公开场景

四川农业大学 2026 年文旅与会展竞赛通知允许跨校区组队，并要求团队至少包含一名旅游管理专业学生；物联网应用创新大赛通知也包含跨学科、跨专业组队和部分赛道人数要求。这说明比赛与组队条件具有可建模的实际场景。

## 4. 产品与业务规则

### 4.1 角色

系统角色分为访客、学生和管理员。队长是某个队伍中的关系角色，不是全局管理员身份。

| 操作                   | 权限                                       |
| ---------------------- | ------------------------------------------ |
| 浏览比赛与公开招募     | 访客、学生、管理员                         |
| 收藏、申请、发布、举报 | 已登录且未受限的学生                       |
| 查看申请详情、发出邀请 | 对应队伍的队长                             |
| 查看成员联系方式       | 对应队伍的有效成员，且联系方式拥有者已授权 |
| 修改比赛与处理举报     | 管理员                                     |

所有权限在后端验证。前端隐藏按钮只用于界面反馈。

### 4.2 学院分类

首页默认勾选全部学院并列出全部比赛；取消全部学院且未选院徽时显示空结果；点击院徽按承办学院多选筛选。搜索及报名状态合并在院徽卡片内。根据 2026-10-04 用户审查反馈，移除类别及“本学院可参加”筛选和对应 URL 参数。承办关系与参赛资格仍分别表达，参赛范围和限制仅展示在比赛卡片与详情中。

参赛范围使用明确枚举：`ALL_SCHOOL`、`SELECTED_COLLEGES`、`OTHER_RULES`。选定学院使用关联表保存，禁止用空数组同时表达“全校开放”和“信息缺失”。对于复杂的专业、年级要求，展示规则摘要和来源，不显示未经实现的“资格已通过”结论。

校区与学院列表根据正式来源维护，不在代码中猜测完整名录。个人资料中的校区与学院属于用户自填信息，不代表学籍认证。

### 4.3 比赛、赛道与项目

- 一条比赛记录代表一个确定的届次；下一届创建新记录，保留历史数据。
- 同一届比赛可包含多个赛道，赛道可记录不同人数与规则摘要。
- 队伍可以关联比赛和赛道；关联赛道时必须校验它属于该比赛。
- 课程、大创和其他项目允许不关联比赛。
- 比赛报名截止时间与队伍招募截止时间分别记录。
- 比赛状态与时间判断由后端计算，不依赖浏览器时钟。

### 4.4 招募状态

队伍业务状态分为 `OPEN`、`PAUSED`、`CLOSED`、`DISBANDED`。后台隐藏状态使用独立字段，不覆盖业务状态。

有效招募必须同时满足：状态为 OPEN、未被隐藏、未达到容量、未超过招募截止时间。列表筛选与申请接口使用同一规则。

队长创建队伍后自动成为有效成员，计入人数上限。满员暂停招募；成员退出后不自动开放，由队长确认。队长不能直接退出，必须移交给已确认的成员或解散队伍。

### 4.5 申请与邀请状态

第一版将申请与邀请记录统一保存于 `applications`，状态为：

```text
PENDING → INVITED → ACCEPTED
PENDING → REJECTED / WITHDRAWN / EXPIRED
INVITED → DECLINED / WITHDRAWN / REVOKED / EXPIRED
```

- PENDING：待队长处理。
- INVITED：队长发出邀请，等待申请人确认。
- ACCEPTED：已确认入队。
- REJECTED：队长拒绝申请。
- WITHDRAWN：申请人撤回。
- DECLINED：申请人拒绝邀请。
- REVOKED：队长撤销邀请。
- EXPIRED：申请或邀请因超时、招募关闭等原因失效。

邀请默认 48 小时有效，且不能超过队伍招募截止时间。邀请不预占名额，页面明确提示“确认时以剩余名额为准”。最后一个名额确认成功后，其他有效邀请和待处理申请由事务统一标记失效并生成通知。

同一人对同一队伍只能有一条有效申请，已在队伍中的用户不能再申请。终态后再次申请需重新创建记录，并经过限频。

### 4.6 并发确认入队

确认入队必须使用数据库事务：

1. 锁定队伍行，再锁定对应申请行；涉及队伍与申请的写操作保持相同锁顺序。
2. 校验身份、账号状态、队伍状态、截止时间和邀请有效期。
3. 检查有效成员数和重复成员关系。
4. 插入或恢复成员关系，更新申请状态。
5. 如果满员，暂停招募并使其余有效申请失效。
6. 在同一事务写入站内通知后提交。

重复确认已成功的同一申请返回当前结果，不增加成员。名额被其他人占用时返回 409 业务冲突。成员数量使用有效成员关系查询，第一版不另外保存可能失真的人数计数。

不同比赛的“不得加入多个队伍”规则不在第一版自动强制执行，因为其适用范围可能涉及赛道、届次或校外系统。平台展示规则并提醒核对，不限制学生在整个网站只能加入一支队伍。

### 4.7 联系方式与内容安全

联系方式独立存储，不出现在公开队伍、公开资料、列表响应或日志中。默认不共享，用户主动授权后，仅向同队有效成员展示。管理员角色本身不获得常规读取私人联系方式的权限。

招募内容采用纯文本，保留换行，不支持原始 HTML。第一版使用默认头像，不提供自定义附件上传；图片需求在核心闭环完成后单独评估。

### 5.2 Tailwind 与按需组件分工

Issue #19 在旧 Web 完整移除 Vant，保留 Tailwind、少量 CSS、--hhr-* 主题与语义工具类；旧端使用 AuthInput、CollegePicker 和 Lucide 静态图标。uni-app 已建立跨端 FormInput／FormPicker／FormDialog 等控件、主题与本地图标资源，按现有能力复用，不把旧端 DOM 或动态 SVG 直接带入微信公共源码。具体适配与验证边界见迁移清单。

检查 Tailwind Preflight 对按钮、输入框、图片和边框的影响；有冲突时针对处理。用户端与管理端是独立应用，管理端依赖不进入 uni 用户端产物。

手机端采用单列布局；桌面端使用最大内容宽度、侧边筛选或多列卡片。旧 Web 筛选通过 URL 恢复；uni 使用页面参数与会话交接，H5 地址栏／刷新／返回完整兼容仍归 #82 验收。

### 5.3 通信与接口约定

采用 REST API，前缀为 `/api/v1`。前端与后端通过 Nginx 同源访问，开发环境由 Vite 代理请求。

后端 DTO 生成 OpenAPI，前端通过 openapi-typescript 获取类型，不直接导入 NestJS DTO 类。数据库模型与接口响应模型分离。

列表返回 `{ items, page, pageSize, hasMore }`，默认 pageSize 为 20、上限 50。第一版不要求每次返回精确总数。排序使用时间和 ID 作为稳定排序键。

错误返回 `{ code, message, requestId, details? }`：参数错误为 400，未登录为 401，无权限为 403，资源不存在为 404，状态或容量冲突为 409，限频为 429，未配置或上游不可用为 503。私人资源可统一返回 404，避免暴露其存在。认证响应及错误响应均要求 `Cache-Control: no-store`。

### 5.4 后端结构

```text
Controller：接收请求、调用 DTO 校验、返回响应
Guard：验证会话与操作权限
Service：处理业务规则、事务和状态转换
Repository：执行 Drizzle 查询，不依赖 HTTP 对象
DatabaseModule：管理连接池、数据库实例和迁移配置
```

NestJS 服务默认采用单例作用域。事务可跨模块调用，但由发起业务的 Service 统一管理；不能让内部 Repository 自行提交事务。

### 5.5 Monorepo 与包边界

项目使用单个 Git 仓库和 pnpm workspace。apps/web、apps/uni、apps/admin 与 apps/api 各有独立 package.json、依赖、开发命令和构建产物；packages/api-types 保存生成类型，packages/client-domain 保存平台无关业务规则。根目录统一保存 pnpm-lock.yaml、格式化配置和 CI 入口。

工作区包名确定为 `@hehuoda/web`、`@hehuoda/uni`、`@hehuoda/admin`、`@hehuoda/api`、`@hehuoda/api-types`、`@hehuoda/client-domain`。本地依赖使用 `workspace:*`；前端对 api-types 使用类型导入，不引入后端运行时代码。packages 不存放数据库凭据、NestJS DTO 类或只能在服务端执行的模块。

根目录 pnpm-workspace.yaml：

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

Node.js 版本记录在 .nvmrc，pnpm 版本记录在根 package.json 的 packageManager 字段。CI 安装采用 `pnpm install --frozen-lockfile`，禁止在工作流中自动修改锁文件。[pnpm workspace 文档](https://pnpm.io/workspaces)

OpenAPI 导出脚本在受控测试配置下运行，不连接学校网站，也不要求生产数据库或密钥。生成接口类型后，CI 检查 Git 差异，发现未提交的类型变化即失败。数据库实体与公开接口之间保持明确边界。

根目录统一脚本约定：

| 命令                  | 职责                                                                      |
| --------------------- | ------------------------------------------------------------------------- |
| pnpm dev              | 同时启动旧 Web/API，uni H5 与管理端单独启动                               |
| pnpm lint             | 检查工作区代码                                                            |
| pnpm format:check     | 检查格式，不自动修改文件                                                  |
| pnpm typecheck        | 前端执行 vue-tsc，后端执行 tsc 类型检查                                   |
| pnpm api:generate     | 导出 OpenAPI 并生成前端接口类型                                           |
| pnpm build            | 按依赖顺序构建前后端                                                      |
| pnpm test:unit        | 前端与后端单元测试，使用 CI 非监听模式                                    |
| pnpm test:integration | Fastify 注入、真实 PostgreSQL 迁移/查询/事务导入，以及采集审核与恢复测试  |
| pnpm test:e2e         | 真实 HTTP 健康/Swagger 与注入式比赛查询、采集发布流程；浏览器闭环另行接入 |

第一版不引入 Turborepo 或 Nx；构建缓存、按变更包执行检查等优化在确有耗时问题后评估。Monorepo 不改变部署拓扑：当前采用独立 Compose 部署 uni H5、API 与 PostgreSQL，Nginx 提供静态资源和同源代理，详见 deployment.md。

### 5.6 GitHub Actions CI

工作流文件为 `.github/workflows/ci.yml`。监听面向 main 的 pull_request，以及 main 的 push；提供 workflow_dispatch 手动运行入口。PR 新提交后重新检查，使用 concurrency 取消同一 PR 的旧运行。整个工作流不按路径跳过，以免必需检查持续处于 Pending 状态。[GitHub 工作流触发说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

当前 CI 使用 GitHub 托管 runner，真实数据库集成与 API HTTP e2e 在 quality 内执行，没有独立浏览器闭环 Job。当前 main 通过记录见 0.1，不等于本次文档已通过远端 CI。

| Job            | 当前工作与门禁                                                                              |
| -------------- | ------------------------------------------------------------------------------------------- |
| quality        | 冻结安装、格式、lint、部署专项、OpenAPI 无差异、类型检查、全工作区构建、单元／集成／API e2e |
| image-smoke    | quality 成功后构建真实 H5/API 镜像并检查查询、路由、备份恢复、失败回滚及数据保留            |
| publish-images | 仅 main push/manual 保存 images.tar.gz 与 release.json；PR 跳过                             |
| ci-gate        | always 汇总，quality 与 image-smoke 须成功；归档上传失败即门禁失败                          |

ci-gate 仍是主分支门禁；以后新增必需 Job 时同步维护 needs 与结果判断。完整浏览器、微信真机与发布准入仍由 #83–#87 交付，不能用镜像冒烟替代。

安装后先检查 PostgreSQL readiness；Playwright 使用 webServer 或明确的 HTTP 就绪检查，不以固定 sleep 判断服务可用。性能压测仍作为手动或独立任务，不把托管 runner 的性能结果直接当作低配生产能力。

保存测试摘要、失败截图、Playwright trace 和必要构建产物，默认保留 7 天；不得上传含密码、Session 或个人联系方式的产物。测试报告关联提交 SHA，便于复现。

CI 默认只授予 `contents: read`，不读取生产 Secret，不在执行 PR 代码的 Job 中赋予合并权限。第三方 Action 锁定到核验过的完整提交 SHA，定期更新。缓存 pnpm store，不跨运行共享会变化的测试数据库或不受校验的构建产物。[GitHub Actions 安全参考](https://docs.github.com/en/actions/reference/security/secure-use)

### 5.7 分支保护与 PR 自动合并

采用 `main` 与任务分支工作方式，命名为 `feat/*`、`fix/*`、`refactor/*`、`docs/*` 或 `chore/*`；创建基线、保留已有改动与分步提交遵循根目录 [AGENTS.md](../AGENTS.md)。main 为稳定演示分支，功能从短期分支通过 PR 合入，不另设长期 develop 分支。组织归属不改变个人提交者身份，也不表示开发人数发生变化。

2026-10-12 的历史只读核验确认仓库已启用 Allow auto-merge 和 merge commit；Squash Merge 也可用，但当前工作流采用 merge commit 保留分步提交。main 已设置分支保护：要求通过 PR 合入、`ci-gate` 成功、分支保持最新、讨论已解决，禁止强制推送和删除，管理员同样受约束。个人开发阶段不要求额外审核人。

当前 [.github/workflows/auto-merge.yml](../.github/workflows/auto-merge.yml) 在 `CI` 的 `workflow_run: completed` 事件后运行：

1. 仅当 CI 成功、来源为 pull_request 且 head repository 为本仓库时进入合并 Job。
2. 查询面向 main 的开放 PR，排除草稿和跨仓库 PR，确认 PR 最新 head SHA 等于本次通过 CI 的 SHA。
3. 使用 `gh pr merge --auto --merge --match-head-commit <SHA>` 开启原生 Auto-merge，最终合并仍由 GitHub 按分支保护决定。
4. 工作流不检出、执行 PR 代码或下载 PR 产物；合并权限与只读 CI 分离，不使用 `--admin` 绕过规则。

当前流程：

```text
推送功能分支并创建非草稿 PR
  → GitHub Actions 执行 CI
  → CI 成功，工作流核对来源与当前 PR head SHA
  → 开启原生 Auto-merge
  → GitHub 等待全部分支保护条件满足
  → merge commit 合入 main
  → 确认实际合并后显式 dispatch main CI
  → 核对分支清理条件后删除远程分支
```

当前机制无需 `automerge` 标签。[PR #5](https://github.com/HeHuoDa/HeHuoDa/pull/5) 已以 merge commit 合入；有对应的 [CI 成功记录](https://github.com/HeHuoDa/HeHuoDa/actions/runs/36961159094)和 [Auto-merge 工作流成功记录](https://github.com/HeHuoDa/HeHuoDa/actions/runs/36961266028)。合并后的 PR 元数据不能单独证明曾处于等待自动合并状态，成功结论需结合工作流记录。

仍需补充故意失败后修复的门禁验收，以及 Fork、Draft、新提交、目标分支变化、冲突场景的验证记录。当前工作流在每次成功 CI 后核对 SHA；没有实现新提交后主动撤销 Auto-merge、移除标签等行为，不能宣称这些能力已经具备。

若未来希望显式控制哪些 PR 自动合并，可另行提出标签触发方案，在 Issue 中确认意图、权限、撤销规则与验收后再实施。标签增强不属于当前必须交付范围。

PR 自动合并与部署已分别实现：确认实际合并后显式 dispatch main CI，Release recovery 检查漏发；Deploy 受 DEPLOY_ENABLED 与 production 环境约束。当前 main 的镜像发布及一次手动部署已有成功记录；历史自动 Deploy skipped 不证明当前开关关闭或生产从未部署，操作与验收边界见[部署说明](deployment.md)。参考：[分支保护文档](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[Auto-merge 文档](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request)、[GitHub CLI 文档](https://cli.github.com/manual/gh_pr_merge)。

### 6.2 约束与索引

- wechat_identities 的 (app_id, open_id) 唯一，auth_tokens 的 access_hash、refresh_hash 唯一且 (session_id, generation) 唯一。
- favorites 的 user_id + competition_id 唯一。
- team_members 的 team_id + user_id 唯一，退出后保留关系并设置 left_at。
- applications 对 PENDING / INVITED 建立同队同申请人的部分唯一索引。
- competition_colleges 的 competition_id + college_id + relation_type 唯一。
- 对学院关联、比赛状态和截止时间、队伍状态与发布时间、申请队伍和状态、通知接收者和时间建立索引。
- capacity 必须大于零；关联赛道的比赛一致性由业务校验保证。
- 有历史业务记录的比赛使用归档，避免删除导致关系断裂。

### 6.3 认证设计

用户端登录采用微信小程序一键登录（ADR-0006）：用户主动登录后首次自动创建平台账号并绑定 (AppID, OpenID)，后续登录定位同一账号；不存在邮箱密码注册、找回或公开管理员注册，H5 不新增登录渠道。默认昵称为“微信用户”，仅本人可改为 trim 后 1–20 字。早期“邮箱密码 + HttpOnly Cookie Session + CSRF”方案已被取代，原 #9 前端表单保留为历史交付与 H5 演示。

平台凭据为高熵随机 Bearer 令牌对：访问凭据 15 分钟，刷新凭据随登录/每次刷新轮换，会话绝对上限 30 天且刷新不延长；数据库只保存 SHA-256 摘要，会话不随进程重启丢失。已消费刷新凭据再次出现即撤销整个会话族；退出撤销当前会话；账号状态每次请求由数据库校验，受限或注销后旧凭据立即不能访问。登录须确认当前平台协议版本，微信 code 仅由服务端向官方固定端点兑换一次，不保存或下发 session_key，UnionID 可空且不作为跨应用合并依据。

微信登录默认关闭（WECHAT_LOGIN_ENABLED），开启时要求服务器配置有效 AppID/AppSecret；关闭时登录与刷新明确返回 503，公开 health 与比赛接口不受影响。登录与刷新失败有来源/账号/全局三档数据库固定窗口限流预算，配置经环境变量；凭据摘要、消费记录与审计按保留期清理。真实微信联调（AppID/AppSecret、HTTPS 合法域名、真机）作为环境验收条件，未完成前不声称生产可用；前端接入、单次刷新协调与冷启动恢复已随 #132 落地，微信登录与统一身份认证已于 2026-10-26 在微信开发者工具完成真实核验，真机与生产 HTTPS 仍未验证。

## 9. 测试与资源基线

### 9.1 必须验证的高风险场景

| 场景                                 | 预期结果                                     | 所属阶段   |
| ------------------------------------ | -------------------------------------------- | ---------- |
| 全校开放且承办学院不同               | 按承办学院匹配，参赛范围提示准确             | 三         |
| 招募正好截止、邀请同时过期           | 服务端拒绝操作，状态不越界                   | 四、五、六 |
| 同一用户连续点击申请或确认           | 不产生重复有效申请或成员                     | 五         |
| 两人争抢最后名额                     | 不超员，失败方收到明确结果                   | 五         |
| 队长移交后原队长审批                 | 原队长不再拥有该权限                         | 四、五     |
| 用户退出后请求队友联系方式           | 被拒绝，前端清理敏感显示                     | 五         |
| 定时任务中断或重复执行               | 请求仍正确，到期处理可恢复                   | 六         |
| 脚本内容和无效筛选参数               | 文本转义、白名单校验，不执行脚本或拼接 SQL   | 三、四     |
| CI 必需 Job 失败、取消或跳过         | ci-gate 不通过，PR 不自动合并                | 一、二、七 |
| CI 通过后 main 已更新                | 按最新 main 重新检查，再允许合并             | 一、七     |

| Fork 或 Draft PR 触发自动合并工作流  | 不启用合并，不执行不可信代码                 | 一；六扩展 |

测试数据库与开发、演示数据分离。数据库事务和并发行为必须用 PostgreSQL 集成测试验证，不能用 ORM mock 证明。

### 9.2 压测方法

性能验证分为单用户基线、只读负载、混合读写、争抢名额四组。数据集可从 1,000 个演示账号、100 条比赛、3,000 条招募起步，再按需要扩大。

并发逐级增加，例如 5、10、20、50 个虚拟用户，每一级先预热，再采集稳定区间。设置用户思考时间，明确实际请求速率，分别报告缓存命中与不命中结果。

目标是找到稳定负载范围，而非预先承诺固定 QPS。作为初步体验目标，可采用普通查询 P95 小于 500ms、非预期错误率小于 1%；达到目标的负载、数据量和机器规格必须同时记录。409 等预期业务冲突单独统计。

### 9.3 低配运行策略

- 生产运行一个 NestJS 进程，默认 5 个 PostgreSQL 连接；使用超时防止请求无限等待。
- 不在生产服务器执行依赖编译、前端构建或压测。
- PostgreSQL 参数保守配置并实测，不能把每个查询的内存额度当作数据库总上限。
- 监控实际进程 RSS；Node.js 堆限制不等于整个进程内存上限。
- 第一版不接收大附件，不启动聊天连接和常驻高频轮询。
- 通知只在页面可见时刷新，定时任务限制每次处理条数。
- 单实例限频可以使用内存存储；扩展到多实例前必须调整会话、调度和限频设计。
- 缓存只用于公开目录等可共享内容，私有响应设置禁止共享缓存。
- 观察 CPU、数据库等待、带宽和查询计划后再优化，避免先引入 Redis 或微服务。
