# 问题跟踪器：GitHub

本仓库的问题与方案记录在 GitHub Issues，使用 `gh` CLI 操作。

仓库为 `jingtll/HeHuoRen`；在工作区外运行命令时显式传入 `--repo jingtll/HeHuoRen`。分诊状态与类别标签参见 [triage-labels.md](triage-labels.md)。

## 约定

- 创建：`gh issue create --title "..." --body "..."`。
- 查看：`gh issue view <编号> --comments`；需要时同时读取标签。
- 列表：`gh issue list`，按状态和标签筛选，并读取正文与评论。
- 需要完整分诊上下文时：`gh issue list --state open --json number,title,body,labels,comments,assignees`；默认列表是分页结果，使用 `--limit` 或 `gh api --paginate` 获取所需范围。
- 评论与标签：使用 `gh issue comment`、`gh issue edit --add-label/--remove-label`。
- 关闭：`gh issue close <编号> --comment "..."`。
- 默认仓库由 `git remote -v` 推断。

## Issue 标题与任务拆分

新建 Issue 的标题使用 `[类型][端别][层次] 具体任务`。类型沿用 `[Task]`、`[Bug]`、`[Feature]`；更新既有 Issue 时保留原有类型前缀，没有类型前缀的历史 Issue 可保持原样，但须补齐端别与层次。

- 端别使用 `[管理端]` 或 `[用户端]`；同时服务两端的共享任务使用 `[管理端/用户端]`。
- 层次使用 `[前端]` 或 `[后端]`。前后端开发原则上拆为独立 Issue，并在正文和原生阻塞关系中记录接口依赖；确实需要整体交付的共享基础设施任务可使用 `[前后端]`，正文说明原因及两层范围。
- 按任务实际交付内容分类：管理端的用户、招募与举报治理仍属于管理端；官方通知采集、候选审核与导入后端属于管理端后端。标题分类不代表已有 HTTP 接口或扩大实施范围。
- 创建或更新时核对端别与层次，替换模板中的 `[端别][层次]` 占位符；已有标识直接校正，保持每类标识仅出现一次。
- 批量整理现有标题默认只处理开放 Issue；修改已关闭历史 Issue 须另获用户明确授权。发布前仍须按上文展示完整内容并获得确认。

示例：

- `[Task][管理端][前端] 完成候选审核与通知版本页面`
- `[Task][管理端][后端] 提供候选审核与通知版本接口`
- `[Task][用户端][前端] 完成个人中心收藏页面`
- `[Task][管理端/用户端][前后端] 完善全栈容器化与部署工作流`

## Pull Requests 是否作为需求入口

**PRs as a request surface: no.** 外部 PR 不进入 issue triage 流程。

## 技能中的 issue 操作约定

- “发布到问题跟踪器”：创建 GitHub Issue。
- “获取关联任务”：运行 `gh issue view <编号> --comments`。
- `/to-spec` 与 `/to-tickets` 使用标签映射中的 `ready-for-agent`；按各技能要求确认方案或任务拆分后发布。
- `/triage` 发布的正文或评论以 `> *This was generated by AI during triage.*` 开头。

## Wayfinding operations

- `/wayfinder` 地图使用 `wayfinder:map` 标签；子任务使用 `wayfinder:research`、`wayfinder:prototype`、`wayfinder:grilling` 或 `wayfinder:task` 标签。
- 子任务优先使用 GitHub 子 issue 关联；不可用时，在地图正文中列出任务，并在子 issue 开头标注 `Part of #<地图编号>`。
- 子 issue 通过 `gh api repos/jingtll/HeHuoRen/issues/<地图编号>/sub_issues` 读取；创建关联时对同一端点发送 POST，传入 `sub_issue_id`。
- 阻塞关系优先使用 GitHub 原生 issue dependencies：对 `repos/jingtll/HeHuoRen/issues/<任务编号>/dependencies/blocked_by` 发送 POST，传入 `issue_id`。关联使用 issue 的数据库 ID，通过 `gh api repos/jingtll/HeHuoRen/issues/<编号> --jq .id` 获取；不使用页面编号或 `node_id`。不可用时，在正文标注 `Blocked by: #<编号>`。
- 查找当前可领取任务时，读取地图的开放子 issue，排除已指派或仍有开放阻塞项的任务，再按地图顺序选择。原生 `issue_dependencies_summary.blocked_by` 表示开放阻塞项数量；使用正文关联时逐一核验阻塞 issue 状态。
- 领取任务时指派给当前用户；完成时先评论结果，再关闭 issue，并把决策摘要补充到地图。

GitHub 的 issue 与 PR 共用编号。遇到不确定的 `#编号` 时，先运行 `gh pr view <编号>`，失败后再运行 `gh issue view <编号>`。

原生关联 API 参见 GitHub 官方[子 issue 文档](https://docs.github.com/en/rest/issues/sub-issues)与[阻塞依赖文档](https://docs.github.com/en/rest/issues/issue-dependencies)。
