# 问题跟踪器：GitHub

本仓库的问题与方案记录在 GitHub Issues，使用 `gh` CLI 操作。

仓库为 `HeHuoRen-Sicau/HeHuoRen`；在工作区外运行命令时显式传入 `--repo HeHuoRen-Sicau/HeHuoRen`。分诊状态与类别标签参见 [triage-labels.md](triage-labels.md)。

## 约定

- 发布前审阅：创建或更新 Issue 前，先展示完整标题、正文、标签及依赖关系；用户明确确认内容和发布后再执行。对方向、示例数据或交互方式的确认不作为发布确认。
- 交付收尾：用户要求“提交并 PR”时，关联 Issue 的交付评论与符合条件时的关闭按 [PR 交付收尾流程](pull-requests.md#关联-issue-交付收尾)默认授权执行；需求内容、标题、标签及依赖修改仍按发布前审阅规则执行。
- 创建：`gh issue create --title "..." --body "..."`。
- 查看：`gh issue view <编号> --comments`；需要时同时读取标签。
- 列表：`gh issue list`，按状态和标签筛选，并读取正文与评论。
- 需要完整分诊上下文时：`gh issue list --state open --json number,title,body,labels,comments,assignees`；默认列表是分页结果，使用 `--limit` 或 `gh api --paginate` 获取所需范围。
- 评论与标签：使用 `gh issue comment`、`gh issue edit --add-label/--remove-label`。
- 关闭：`gh issue close <编号> --comment "..."`。
- 默认仓库由 `git remote -v` 推断。

## Issue 标题与任务拆分

新建 Issue 的标题使用 `[类型][端别][层次] 具体任务`。类型沿用 `[Task]`、`[Bug]`、`[Feature]`；更新既有 Issue 时保留原有类型前缀，没有类型前缀的历史 Issue 可保持原样，但须补齐端别与层次。

- 端别使用 `[管理端]` 或 `[用户端]`；同时服务两端的共享任务使用 `[管理端/用户端]`。
- 层次使用 `[前端]` 或 `[后端]`。前后端开发原则上拆为独立 Issue，并在正文和原生阻塞关系中记录接口依赖；确实需要整体交付的共享基础设施任务可使用 `[前后端]`，正文说明原因及两层范围。
- 按任务实际交付内容分类：管理端的用户、招募与举报治理仍属于管理端；官方通知采集、候选审核与导入后端属于管理端后端。标题分类不代表已有 HTTP 接口或扩大实施范围。
- 创建或更新时核对端别与层次，替换模板中的 `[端别][层次]` 占位符；已有标识直接校正，保持每类标识仅出现一次。
- 批量整理现有标题默认只处理开放 Issue；修改已关闭历史 Issue 须另获用户明确授权。发布前仍须按上文展示完整内容并获得确认。

示例：

- `[Task][管理端][前端] 完成候选审核与通知版本页面`
- `[Task][管理端][后端] 提供候选审核与通知版本接口`
- `[Task][用户端][前端] 完成个人中心收藏页面`
- `[Task][管理端/用户端][前后端] 完善全栈容器化与部署工作流`

## Issue 可开工标准

每次新建 Issue 均执行以下流程，覆盖直接创建、子任务、批量拆票、分诊和技能生成的任务。更新任务范围时也重新核对。可开工是正文质量要求，不使用 `ready-for-agent` 标签表达。

### 起草与核实

1. 读取相关代码、项目约定及关联 Issue／PR 的正文、关键评论和当前状态，核对现状与已完成范围。能从仓库或远端查明的事实由 Agent 自行核实；记录核查基线或日期，区分已核实事实、用户决策和待验证假设。
2. 把当前聊天中影响执行的结论写入正文。引用外部方案、父 Issue 或 ADR 时，给出可访问的具体链接，并在本 Issue 摘要说明与本任务有关的决定；链接不能代替任务范围和验收标准。本地草稿、未上传截图或聊天记录不能成为执行的必要前提。
3. 按下文结构填写完整正文；简单任务可合并章节，不适用项简述原因。按任务需要提供足够信息，不为凑格式编造接口、文件路径或实现细节。
4. 执行发布前自检，通过后展示完整标题、正文、标签和依赖关系，按本文件的发布前审阅约定等待用户明确确认。发布后回读远端内容与依赖，确认与获批草稿一致。

### 正文结构与必备信息

- **背景与目标**：谁在什么场景遇到什么问题，当前行为与期望结果有什么差异，完成后获得什么可观察的结果。Bug 补充环境、前置条件、复现步骤、实际结果和预期结果；无法稳定复现时说明已知证据。
- **范围与非目标**：明确端别、前后端责任、涉及的页面／流程／模块和交付物，列出本次不做的内容；区分设计、会话 Demo、真实接口接入和生产交付。每个子任务独立写明自己的范围。
- **现状与实施入口**：列出已核实的相关文件、路由、模块、接口或配置入口及其作用，链接相关 Issue／PR／ADR；说明哪些能力已有、哪些需要新增或调整。入口用于导航，具体实现由执行 Agent 结合现行代码确定。
- **行为与契约**：写清主要流程、业务规则、权限、输入输出、数据约束和适用的边界／异常处理。涉及接口时记录方法、路径、关键字段、错误语义与契约来源，核对后端最新已合并实现；尚未存在的接口明确标为拟定契约，并说明由谁提供、何时能接入。UI 任务说明交互、样式依据、加载／空／错误状态和长文本处理。
- **依赖与开工条件**：明确无依赖，或逐项列出阻塞任务、所需产物及解除条件；核对依赖当前状态，按本文件原生阻塞关系约定记录。区分可独立推进的工作与受阻部分；拆出的任务各自包含所需契约和验收，不要求执行者自行从兄弟任务或聊天中拼出需求。
- **验收与验证**：使用可勾选条目描述“前置条件／操作／可观察的预期结果”，覆盖主要流程及相关边界、权限与失败场景；给出测试入口或验证方式、必要环境与数据准备、完成证据要求。已有命令须核对仓库实际配置；待新增测试或脚本明确标注。区分本地、模拟、真实服务和生产验证，不能用构建通过替代业务验收。
- **风险与待确认项**：写出影响范围、兼容性及适用的数据变更／回滚要求；用户端任务记录 H5 与普通 uni-app／微信小程序的具体迁移影响、方案和待验证项。待确认项说明影响及解决方式；没有则明确写明。

用户端 UI 任务的验收须纳入 `AGENTS.md` 要求的 320／375／390／430px 视口与受影响状态，并分别说明浏览器模拟、真机及目标端的验证要求。其他任务按实际范围设置验收条件。

### 发布前自检

以“一个未参与聊天、刚打开仓库的 Agent”为读者逐项检查：

- 能否仅凭正文、仓库和明确链接，确定要解决的问题、改动范围、实施入口、业务约束与完成条件？
- 正文是否仍有“按之前讨论”“参考上图”“完善相关功能”等依赖隐含上下文的表达，或未填占位符、互相矛盾的规则？逐项改成具体内容。
- 是否存在会改变范围、接口、权限、数据安全或验收结果的未决问题？先自行查证，无法查证的向用户集中澄清；澄清前保留草稿，不把它作为可开工实现任务发布。
- 若任务确为调研或决策，是否明确了要回答的问题、调查范围、约束、预期产物和完成标准？此类任务可把解决未知项作为交付物；实现任务有外部阻塞时须写清解除条件，解除前不宣称可立即开工。
- 标题、标签、正文范围及阻塞关系是否一致，且每项验收都能实际判定通过或失败？

任一适用项不满足时，补齐后再提交用户审阅；用户确认的内容若随后发生实质变化，重新展示变更后的完整草稿并确认发布。

## Pull Requests 是否作为需求入口

**PRs as a request surface: no.** 外部 PR 不进入 issue triage 流程。

## 技能中的 issue 操作约定

- “发布到问题跟踪器”：创建 GitHub Issue。
- “获取关联任务”：运行 `gh issue view <编号> --comments`。
- `/to-spec` 与 `/to-tickets` 按本项目标签映射执行，跳过技能默认的 `ready-for-agent` 标签；完整方案或任务正文先交用户审阅，明确确认发布后再创建或更新 Issue。
- `/triage` 发布的正文或评论以 `> *This was generated by AI during triage.*` 开头。

## Wayfinding operations

- `/wayfinder` 地图使用 `wayfinder:map` 标签；子任务使用 `wayfinder:research`、`wayfinder:prototype`、`wayfinder:grilling` 或 `wayfinder:task` 标签。
- 子任务优先使用 GitHub 子 issue 关联；不可用时，在地图正文中列出任务，并在子 issue 开头标注 `Part of #<地图编号>`。
- 子 issue 通过 `gh api repos/HeHuoRen-Sicau/HeHuoRen/issues/<地图编号>/sub_issues` 读取；创建关联时对同一端点发送 POST，传入 `sub_issue_id`。
- 阻塞关系优先使用 GitHub 原生 issue dependencies：对 `repos/HeHuoRen-Sicau/HeHuoRen/issues/<任务编号>/dependencies/blocked_by` 发送 POST，传入 `issue_id`。关联使用 issue 的数据库 ID，通过 `gh api repos/HeHuoRen-Sicau/HeHuoRen/issues/<编号> --jq .id` 获取；不使用页面编号或 `node_id`。不可用时，在正文标注 `Blocked by: #<编号>`。
- 查找当前可领取任务时，读取地图的开放子 issue，排除已指派或仍有开放阻塞项的任务，再按地图顺序选择。原生 `issue_dependencies_summary.blocked_by` 表示开放阻塞项数量；使用正文关联时逐一核验阻塞 issue 状态。
- 领取任务时指派给当前用户；完成时先评论结果，再关闭 issue，并把决策摘要补充到地图。

GitHub 的 issue 与 PR 共用编号。遇到不确定的 `#编号` 时，先运行 `gh pr view <编号>`，失败后再运行 `gh issue view <编号>`。

原生关联 API 参见 GitHub 官方[子 issue 文档](https://docs.github.com/en/rest/issues/sub-issues)与[阻塞依赖文档](https://docs.github.com/en/rest/issues/issue-dependencies)。
